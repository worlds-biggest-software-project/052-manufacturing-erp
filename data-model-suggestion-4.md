# Data Model Suggestion 4: Graph-Relational (PostgreSQL + Graph Layer)

> Project: Manufacturing ERP · Created: 2026-05-12

## Philosophy

This model uses PostgreSQL relational tables for transactional CRUD operations (work orders, inventory, job cards) and layers a property graph structure on top for relationship-heavy queries (multi-level BOM traversal, supply chain traceability, where-used analysis, impact analysis, and conflict-of-interest detection). The graph layer is implemented using a generic `graph_node` / `graph_edge` table pair in PostgreSQL, avoiding the need for a separate graph database like Neo4j while providing graph query patterns through recursive CTEs and path-based queries.

Manufacturing is fundamentally about relationships: items contain other items (BOM), operations follow operations (routing), lots consume lots (traceability), equipment belongs to work centers that belong to plants, and suppliers provide materials that go into products that ship to customers. These relationships form complex, multi-hop graphs that relational JOINs handle poorly beyond 2-3 levels. A graph model makes multi-level BOM explosion, forward/backward lot traceability, "where-used" analysis, and supply chain impact assessment natural operations rather than recursive CTE gymnastics.

The design draws from Volvo's use of Neo4j for configurable BOMs (CBOM), from Neo4j's published supply chain optimization patterns, and from the ISA-95 resource hierarchy model. The relational side handles high-volume transactional writes (telemetry, inventory movements, job card completions) where graph overhead would be wasteful. The graph side handles the relationship queries that provide the most value to AI agents — the dynamic scheduler needs to traverse equipment capability graphs, the quality predictor needs to trace material genealogy graphs, and the BOM assistant needs to explore component substitution networks.

**Best for:** Manufacturers with deep BOM structures (10+ levels), complex supply chains, "where-used" analysis requirements, lot genealogy tracing, and AI agents that need to reason over relationships (scheduler, quality predictor, BOM assistant).

**Trade-offs:**
- (+) Multi-level BOM explosion is a natural graph traversal, not a recursive CTE
- (+) Forward and backward lot traceability ("which finished goods used lot X?") is a graph walk
- (+) Where-used analysis ("which products are affected by a supplier recall?") is a graph query
- (+) AI agents can traverse capability, substitution, and dependency graphs naturally
- (+) Supply chain impact analysis (ripple effects of a supplier disruption) is immediate
- (+) Can evolve to a dedicated graph database (Neo4j, Amazon Neptune) if graph queries become the bottleneck
- (-) Two query paradigms: SQL for transactional data, graph traversal for relationship data
- (-) Graph sync overhead: changes to relational BOM/routing must propagate to graph tables
- (-) PostgreSQL graph queries (recursive CTEs on graph_edge) are slower than native graph databases for very deep traversals
- (-) Developers must understand both relational and graph modeling concepts
- (-) More complex write path: every BOM/routing change requires updating both relational and graph tables

## Standards Alignment

| Standard | How It's Used |
|----------|---------------|
| ISA-95 / IEC 62264 | ISA-95 equipment hierarchy (enterprise > site > area > work center > equipment) is a graph with `CONTAINS` edges; personnel qualifications are `QUALIFIED_FOR` edges between person and equipment class nodes |
| ISO 9001:2015 | Lot traceability graph enables forward/backward trace queries required by ISO 9001; non-conformance impact analysis uses graph traversal |
| AS9100 Rev D | Configuration management uses graph relationships to trace which assemblies use which revision of a component |
| GS1 EPCIS | EPCIS traceability events map to graph edges between lot nodes: `CONSUMED_BY`, `PRODUCED_FROM`, `SHIPPED_TO` |
| B2MML v0700 | BOM hierarchy and routing sequences are naturally graph structures; B2MML data exchange can be generated by traversing the graph |
| MTConnect / OPC-UA | Equipment hierarchy and component containment are graph structures |
| ISA-95 Equipment Model | ISA-95 defines equipment as a hierarchy: enterprise > site > area > process cell > unit — modeled as `CONTAINS` edges in the graph |

## Graph Layer Tables

```sql
-- ============================================================
-- GRAPH LAYER — Generic Property Graph in PostgreSQL
-- ============================================================

-- Nodes represent any entity that participates in relationships
CREATE TABLE graph_node (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL,
    node_type       TEXT NOT NULL,
    -- node_type values:
    -- 'item', 'bom', 'work_center', 'equipment', 'person',
    -- 'lot', 'work_order', 'supplier', 'customer', 'site',
    -- 'equipment_class', 'personnel_class', 'operation'
    
    -- Link to the relational entity
    entity_id       UUID NOT NULL,         -- FK to the relational table (not enforced generically)
    entity_table    TEXT NOT NULL,          -- 'item', 'equipment', 'lot', etc.
    
    -- Searchable label
    label           TEXT NOT NULL,          -- human-readable: 'PART-A100', 'CNC-L-003', 'L2026-0512-001'
    
    -- Graph properties
    properties      JSONB NOT NULL DEFAULT '{}',
    -- properties vary by node_type; examples:
    -- item: {"item_type": "finished_good", "uom": "EA", "standard_cost": 125.50}
    -- equipment: {"status": "operational", "work_center": "WC-LATHE-01"}
    -- lot: {"status": "available", "quantity": 500, "manufactured_date": "2026-05-12"}
    
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, entity_table, entity_id)
);

CREATE INDEX idx_gn_type ON graph_node(node_type);
CREATE INDEX idx_gn_label ON graph_node(tenant_id, label);
CREATE INDEX idx_gn_entity ON graph_node(entity_table, entity_id);
CREATE INDEX idx_gn_props ON graph_node USING GIN (properties);

-- Edges represent directed relationships between nodes
CREATE TABLE graph_edge (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL,
    
    -- Relationship
    source_node_id  UUID NOT NULL REFERENCES graph_node(id),
    target_node_id  UUID NOT NULL REFERENCES graph_node(id),
    edge_type       TEXT NOT NULL,
    -- edge_type values:
    -- BOM: 'CONTAINS' (parent item -> child item)
    -- Routing: 'FOLLOWED_BY' (operation -> next operation)
    -- Equipment: 'LOCATED_IN' (equipment -> work_center)
    -- Personnel: 'QUALIFIED_FOR' (person -> equipment_class)
    -- Lot trace: 'CONSUMED_BY' (source lot -> work order)
    -- Lot trace: 'PRODUCED_FROM' (work order -> output lot)
    -- Supply: 'SUPPLIED_BY' (item -> supplier)
    -- Alternates: 'SUBSTITUTE_FOR' (alt item -> primary item)
    -- Hierarchy: 'PART_OF' (work center -> site)
    -- Assignment: 'ASSIGNED_TO' (work order -> equipment)
    -- Quality: 'FAILED_ON' (NCR -> lot)
    -- Dependency: 'DEPENDS_ON' (work order -> work order)
    
    -- Edge properties
    properties      JSONB NOT NULL DEFAULT '{}',
    -- properties vary by edge_type; examples:
    -- CONTAINS: {"quantity": 4, "uom": "EA", "scrap_factor": 0.02, "bom_id": "uuid",
    --            "effective_from": "2026-01-01", "effective_to": null}
    -- FOLLOWED_BY: {"routing_id": "uuid", "sequence": 20, "overlap_pct": 0}
    -- QUALIFIED_FOR: {"level": 3, "certification": "AWS D1.1", "expires": "2027-03-15"}
    -- CONSUMED_BY: {"quantity": 25.5, "consumed_at": "2026-05-12T08:30:00Z"}
    -- SUBSTITUTE_FOR: {"priority": 1, "approval_status": "approved", "cost_delta": 0.15}
    
    -- Temporal validity (for time-bounded relationships)
    valid_from      TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_to        TIMESTAMPTZ,           -- NULL = currently valid
    
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_ge_source ON graph_edge(source_node_id);
CREATE INDEX idx_ge_target ON graph_edge(target_node_id);
CREATE INDEX idx_ge_type ON graph_edge(edge_type);
CREATE INDEX idx_ge_source_type ON graph_edge(source_node_id, edge_type);
CREATE INDEX idx_ge_target_type ON graph_edge(target_node_id, edge_type);
CREATE INDEX idx_ge_valid ON graph_edge(valid_from, valid_to);
CREATE INDEX idx_ge_props ON graph_edge USING GIN (properties);
```

## Graph Query Examples

### Multi-Level BOM Explosion (Graph Walk)

```sql
-- Explode a BOM to all levels using graph traversal
-- Faster and more natural than recursive CTE on bom_line table
WITH RECURSIVE bom_tree AS (
    -- Anchor: direct children of the parent item
    SELECT
        ge.target_node_id AS node_id,
        gn.label AS item_label,
        gn.properties->>'item_type' AS item_type,
        (ge.properties->>'quantity')::NUMERIC AS quantity,
        ge.properties->>'uom' AS uom,
        (ge.properties->>'scrap_factor')::NUMERIC AS scrap_factor,
        1 AS depth,
        ARRAY[ge.source_node_id] AS path,
        gn.label AS path_labels
    FROM graph_node parent
    JOIN graph_edge ge ON ge.source_node_id = parent.id AND ge.edge_type = 'CONTAINS'
    JOIN graph_node gn ON gn.id = ge.target_node_id
    WHERE parent.entity_id = :parent_item_id
      AND parent.node_type = 'item'
      AND (ge.valid_to IS NULL OR ge.valid_to > now())

    UNION ALL

    -- Recursive: children of children
    SELECT
        ge.target_node_id,
        gn.label,
        gn.properties->>'item_type',
        (ge.properties->>'quantity')::NUMERIC * bt.quantity,
        ge.properties->>'uom',
        (ge.properties->>'scrap_factor')::NUMERIC,
        bt.depth + 1,
        bt.path || ge.source_node_id,
        bt.path_labels || ' > ' || gn.label
    FROM bom_tree bt
    JOIN graph_edge ge ON ge.source_node_id = bt.node_id AND ge.edge_type = 'CONTAINS'
    JOIN graph_node gn ON gn.id = ge.target_node_id
    WHERE NOT (ge.source_node_id = ANY(bt.path))  -- cycle prevention
      AND bt.depth < 20
      AND (ge.valid_to IS NULL OR ge.valid_to > now())
)
SELECT * FROM bom_tree ORDER BY depth, item_label;
```

### Where-Used Analysis (Reverse BOM Traversal)

```sql
-- "Which finished goods use component PART-R100K-0805?"
-- This is a REVERSE graph traversal — follow CONTAINS edges backwards
WITH RECURSIVE where_used AS (
    -- Anchor: find the component node
    SELECT
        ge.source_node_id AS node_id,
        gn.label AS parent_label,
        gn.properties->>'item_type' AS parent_type,
        (ge.properties->>'quantity')::NUMERIC AS quantity_per,
        1 AS depth,
        ARRAY[ge.target_node_id] AS path
    FROM graph_node component
    JOIN graph_edge ge ON ge.target_node_id = component.id AND ge.edge_type = 'CONTAINS'
    JOIN graph_node gn ON gn.id = ge.source_node_id
    WHERE component.label = 'PART-R100K-0805'
      AND component.node_type = 'item'

    UNION ALL

    -- Recursive: climb up the BOM tree
    SELECT
        ge.source_node_id,
        gn.label,
        gn.properties->>'item_type',
        (ge.properties->>'quantity')::NUMERIC,
        wu.depth + 1,
        wu.path || ge.target_node_id
    FROM where_used wu
    JOIN graph_edge ge ON ge.target_node_id = wu.node_id AND ge.edge_type = 'CONTAINS'
    JOIN graph_node gn ON gn.id = ge.source_node_id
    WHERE NOT (ge.source_node_id = ANY(wu.path))
      AND wu.depth < 20
)
SELECT parent_label, parent_type, depth
FROM where_used
WHERE parent_type = 'finished_good'
ORDER BY depth;
```

### Lot Genealogy — Forward Trace

```sql
-- "Where did lot L2026-0512-001 end up?" (forward traceability)
-- Follows: lot -> CONSUMED_BY -> work_order -> PRODUCED_FROM -> output_lot -> ...
WITH RECURSIVE forward_trace AS (
    SELECT
        gn.id AS node_id,
        gn.label,
        gn.node_type,
        gn.properties AS props,
        0 AS depth,
        ARRAY[gn.id] AS path
    FROM graph_node gn
    WHERE gn.label = 'L2026-0512-001'
      AND gn.node_type = 'lot'

    UNION ALL

    SELECT
        gn.id,
        gn.label,
        gn.node_type,
        gn.properties,
        ft.depth + 1,
        ft.path || gn.id
    FROM forward_trace ft
    JOIN graph_edge ge ON ge.source_node_id = ft.node_id
        AND ge.edge_type IN ('CONSUMED_BY', 'PRODUCED_FROM')
    JOIN graph_node gn ON gn.id = ge.target_node_id
    WHERE NOT (gn.id = ANY(ft.path))
      AND ft.depth < 10
)
SELECT label, node_type, props, depth
FROM forward_trace
ORDER BY depth;
```

### Supplier Impact Analysis

```sql
-- "If supplier ACME-STEEL goes down, which work orders are affected?"
-- Traverses: supplier -> SUPPLIED_BY (reverse) -> items -> where_used -> work_orders

WITH affected_items AS (
    -- Items supplied by the at-risk supplier
    SELECT ge.source_node_id AS item_node_id
    FROM graph_node supplier
    JOIN graph_edge ge ON ge.target_node_id = supplier.id
        AND ge.edge_type = 'SUPPLIED_BY'
    WHERE supplier.label = 'ACME-STEEL'
      AND supplier.node_type = 'supplier'
),
affected_products AS (
    -- Climb up BOM to find all products using those items
    WITH RECURSIVE climb AS (
        SELECT ai.item_node_id AS node_id, 0 AS depth
        FROM affected_items ai

        UNION ALL

        SELECT ge.source_node_id, c.depth + 1
        FROM climb c
        JOIN graph_edge ge ON ge.target_node_id = c.node_id
            AND ge.edge_type = 'CONTAINS'
        WHERE c.depth < 20
    )
    SELECT DISTINCT node_id FROM climb
)
-- Find active work orders for affected products
SELECT wo.wo_number, wo.status, wo.planned_start, wo.item_id,
       gn.label AS affected_item
FROM affected_products ap
JOIN graph_node gn ON gn.id = ap.node_id
JOIN item i ON i.id = gn.entity_id
JOIN work_order wo ON wo.item_id = i.id
WHERE wo.status IN ('draft', 'released', 'in_progress')
ORDER BY wo.planned_start;
```

## Graph Synchronisation

When relational entities are created or modified, the graph layer must be updated. This is handled by database triggers or application-level event handlers.

```sql
-- ============================================================
-- GRAPH SYNC TRIGGER (Example: item creation syncs to graph_node)
-- ============================================================

CREATE OR REPLACE FUNCTION sync_item_to_graph()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO graph_node (tenant_id, node_type, entity_id, entity_table, label, properties)
        VALUES (
            NEW.tenant_id,
            'item',
            NEW.id,
            'item',
            NEW.item_number,
            jsonb_build_object(
                'item_type', NEW.item_type,
                'uom', NEW.uom,
                'standard_cost', NEW.standard_cost,
                'lot_tracked', NEW.lot_tracked
            )
        );
    ELSIF TG_OP = 'UPDATE' THEN
        UPDATE graph_node
        SET label = NEW.item_number,
            properties = jsonb_build_object(
                'item_type', NEW.item_type,
                'uom', NEW.uom,
                'standard_cost', NEW.standard_cost,
                'lot_tracked', NEW.lot_tracked
            ),
            updated_at = now()
        WHERE entity_id = NEW.id AND entity_table = 'item';
    ELSIF TG_OP = 'DELETE' THEN
        -- Soft delete: mark edges as expired rather than deleting
        UPDATE graph_edge SET valid_to = now()
        WHERE source_node_id IN (SELECT id FROM graph_node WHERE entity_id = OLD.id AND entity_table = 'item')
           OR target_node_id IN (SELECT id FROM graph_node WHERE entity_id = OLD.id AND entity_table = 'item');
        DELETE FROM graph_node WHERE entity_id = OLD.id AND entity_table = 'item';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_item_graph_sync
    AFTER INSERT OR UPDATE OR DELETE ON item
    FOR EACH ROW EXECUTE FUNCTION sync_item_to_graph();

-- Similar triggers for: equipment, work_center, person, lot, work_order, supplier
-- BOM line insertion creates CONTAINS edges
-- Routing operation insertion creates FOLLOWED_BY edges
-- Material issue to work order creates CONSUMED_BY edges
-- Work order completion creates PRODUCED_FROM edges
```

## Key Design Decisions

1. **BOM hierarchy lives in the graph, not in relational tables** — Instead of a `bom_line` junction table with recursive CTEs for explosion, BOM parent-child relationships are `CONTAINS` edges in the graph. This makes multi-level BOM explosion, where-used analysis, and substitution discovery natural graph traversals.

2. **Lot genealogy is modeled as a graph** — Material consumption (`CONSUMED_BY`) and production output (`PRODUCED_FROM`) are graph edges between lot and work order nodes. Forward and backward traceability become graph walks rather than multi-table JOINs.

3. **Equipment capability is a graph** — The ISA-95 equipment hierarchy (site > area > work center > equipment) and personnel qualifications (`QUALIFIED_FOR`) are graph edges. The AI scheduler traverses this graph to find capable equipment and qualified operators.

4. **Temporal edges support historical graph queries** — Every graph edge has `valid_from` and `valid_to` timestamps. Querying the graph "as of date X" is done by adding `AND valid_from <= X AND (valid_to IS NULL OR valid_to > X)` to edge filters.

5. **Graph sync is trigger-driven** — Database triggers on relational tables automatically create/update/expire corresponding graph nodes and edges. The application never writes to the graph layer directly — it writes to relational tables, and triggers propagate to the graph.

6. **Supplier relationships are first-class graph edges** — Each item-supplier relationship is a `SUPPLIED_BY` edge with properties (lead time, cost, MOQ). Supplier impact analysis ("if this supplier fails, what is affected?") is a graph traversal that climbs through BOMs to find all affected finished goods and active work orders.

7. **Component substitution is a graph network** — `SUBSTITUTE_FOR` edges between item nodes create a substitution network. The AI scheduler and BOM assistant can query this graph to find approved alternates when a primary component is unavailable.

8. **Transactional operations remain relational** — High-volume writes (inventory transactions, job card updates, telemetry) use relational tables. The graph layer is for read-heavy relationship queries, not transactional throughput.

9. **Graph can migrate to Neo4j if needed** — The `graph_node`/`graph_edge` schema is deliberately simple and maps directly to a labeled property graph. If graph query performance becomes a bottleneck (very deep supply chains, real-time traversals), the graph layer can be migrated to Neo4j or Amazon Neptune with a straightforward ETL.

10. **AI agents are the primary beneficiaries** — The graph model is designed for the AI agents described in the project requirements: the dynamic scheduler traverses equipment capability graphs, the quality predictor traces material genealogy, and the BOM assistant explores component substitution networks. Relational queries would require complex multi-join logic; the graph makes these natural.
